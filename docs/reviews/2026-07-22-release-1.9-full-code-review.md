## 发现（按严重级别）

### Critical

#### C1. 银行流水号全局唯一约束 + NULL 唯一性，会卡死导入/复核

**证据**：`backend/app/models/bank_receipt.py`

```python
UniqueConstraint("bank_serial_number", name="uq_bank_receipt_serial")
```

PostgreSQL 下：

1. **多个 `NULL` 流水号可并存**（唯一约束不拦 NULL），识别失败/未解析流水号的回单不会被约束挡住。
2. 一旦解析出 **相同流水号**（OCR 误读、同一流水不同 PDF 裁剪、人工复核手填重复），`review`/`process` 会直接撞 `IntegrityError`。
3. 业务上“流水号可选、人工后补”与“全局唯一非空”不匹配。

**建议**：

- 改为 **partial unique index**：`WHERE bank_serial_number IS NOT NULL`
- 或唯一范围改为 `(bank_serial_number, amount, transaction_at)` / 业务日维度
- 应用层在 `process`/`review` 做友好冲突提示，不要裸抛 DB 异常

---

#### C2. 回单/发票「清除」只把 `amount` 置 0，合同汇总/报表未过滤 `posting_status`

**证据**：

- clear：`bank_receipt.py` / `invoice_import/service.py` → `formal.amount=0; posting_status="cleared"`
- 汇总仍无脑 `sum(amount)`：
  - `contract_upstream_service.py`：`func.sum(FinanceUpstreamReceipt.amount)` / `sum(r.amount for r in contract.receipts)`
  - `contract_downstream_service.py`、`contract_management_service.py` 同理
  - `reports/exports.py`、`contract_search.py` 同理

当前“碰巧正确”仅因为清后金额为 0。一旦：

- 报表要展示“原金额/冲销历史”
- 有人改成保留原金额只标 `cleared`
- 手工改库 / 未来半冲销

汇总就会错。**`posting_status` 已写入但未成为查询不变量**。

**建议**：所有金额汇总统一加<br>
`WHERE posting_status = 'active'`（或 `!= 'cleared'`），并补报表/列表单测。

---

#### C3. 回单确认几乎不校验状态，可对 `ignored` / `failed` / `processing` 入账

**证据**：`BankReceiptService.confirm`

```python
if item.status == "confirmed": return item
if item.direction not in {"receipt","payment"} or item.transaction_at is None: ...
# 没有限制 status 必须是 ready
```

对比 `allocate` 会拦 `confirmed/processing/ignored`，`confirm` 却不拦。
API 可直接 `POST /items/{id}/confirm` 绕过前端 `status==='ready'`。

**建议**：仅允许 `ready`（及明确设计的 re-post 状态）；`ignored/failed/processing/needs_review` 一律拒绝。

### High

#### H1. 回单确认允许“零分摊入账”

`drafts = [a for a in item.allocations if a.status=="draft"]`
空列表时：

```python
validate_receipt_allocation_total(item.amount, [])
# total=0；若 amount 非 0 → 会报错
# 若 amount 为 None → 也会报错
# 但若 amount 恰好为 0（坏数据/误复核）→ 可确认成功且不产生 formal
```

更关键的是：前端把“有分摊”当 `ready` 的弱信号，后端 `allocate` 不校验“分摊合计是否已等于金额”，可在合计未齐时把 status 置 `ready` 并确认失败或半成功。

**建议**：

- `confirm` 强制 `len(drafts) >= 1`
- `allocate` 只改状态为 `ready` 当且仅当草稿合计 == 金额；否则保持 `needs_review`

---

#### H2. 发票 `confirm_item` 可确认 `ignored` 状态

`InvoicePostingService.confirm_item` 只 early-return `confirmed`，**不拒绝 `ignored`**。
只要仍有 draft 分摊，可对已忽略发票重新挂账（权限用户直接打 API）。

**建议**：`confirmation_status in {"draft","cleared"}` 才允许确认。

---

#### H3. 清除后重新挂账：回单路径缺少 `posting_version` / 草稿复位机制

发票侧：`clear` 保留历史 allocation，再 `create_allocation` 新 draft，`confirm` 只认 draft —— 设计清楚。
回单侧：`clear` 把 **所有** allocation 标 `cleared`，但：

- 没有 `posting_version`
- `confirm` 只取 `draft`
- `allocate` 在 `cleared` 状态允许新增（`status not in confirmed/processing/ignored`）

路径可用，但：

- `ignore` **允许对 `cleared` 再忽略**（`status in needs_review/ready/cleared`），会把已清除入账记录标成 ignored，语义混乱
- 清除后 formal 行仍在（amount=0），列表/UI 可能仍显示“幽灵记录”

---

#### H4. 并发上传同一 PDF：应用层查重 + 无事务锁

```python
duplicate = await self.db.scalar(...sha256...)
# 无 with_for_update / 无先插后撞唯一
...
commit  # 依赖 uq_bank_receipt_sha256
```

并发双传会一个 500（IntegrityError）而非业务 ValidationError。
应捕获唯一冲突并转友好错误。

---

#### H5. BackgroundTasks 处理回单：进程内、无重试、worker 重启即丢

`process_batch` 用 FastAPI `BackgroundTasks`：

- 多 worker 下行为不确定
- 部署滚动时任务可丢失
- 异常只写 `failed`，无死信/告警

对财务 OCR 可接受 MVP，但生产要有队列或至少定时扫 `uploaded/processing` 补偿。

---

#### H6. 菜单权限错位：回单挂在“发票”菜单，后端却要 PAYMENTS 权限

- 侧栏：`canViewInvoices` → `/invoice-imports`（发票+回单 Tab）
- 回单 API：`VIEW_PAYMENTS` / `CREATE_PAYMENTS` / `EDIT_PAYMENTS` / `DELETE_PAYMENTS`

结果：

- 能看发票的人不一定能用回单 Tab（接口 403）
- 能管付款的人若无发票权限则进不了工作台

**建议**：拆独立菜单或前端按 `canViewPayments` 控制回单 Tab。

### Medium

#### M1. `upload.filename` 可能为 `None` → `AttributeError`

```python
if not upload.filename.lower().endswith(".pdf")
```

应先规范化 `filename or ""`。

---

#### M2. PDF 页数检测可被绕过

`re.findall(rb"/Type\s*/Page\b", data)` 可被构造 PDF 欺骗；页数限制只能当弱防护。
真正限制应在解析阶段（pypdf page count）+ 文件大小。

---

#### M3. MinerU SSRF 防护有死角

`_validate_external_api_url` 拦了 private/loopback/link-local/reserved，但：

- 仍允许 **http**（明文密钥）
- DNS rebinding（校验时公网、请求时转内网）未做
- 未禁 `metadata` 主机名类云环境特殊域名（部分场景）

密钥用 Fernet + `CONFIG_ENCRYPTION_KEY` 方向正确；**生产必须强制配置且不可轮转丢失**（注释已写，需部署检查）。

---

#### M4. 服务层从 `app.routers.system` 导入 `_reveal_secret`

`bank_receipt.process` → `from app.routers.system import _reveal_secret, _validate_external_api_url`
路由层工具函数被服务层依赖，循环导入风险与分层破坏。应抽到 `app.core.secrets` / `app.services.system_config`。

---

#### M5. 回单匹配候选过于粗糙

`search(counterparty)` 仅 `contract_name ILIKE`，固定 score=80，无金额/账号信号。
误推荐风险高，需人工强依赖（当前 UI 强制选合同，尚可接受）。

---

#### M6. 零星用工财务删除无审计、无“已入账不可删”保护

`DELETE .../finance/{kind}/{record_id}` 直接删；
若记录来自发票导入/回单（`source_*` 字段存在），可造成溯源断裂。

---

#### M7. 前端 `BankReceiptWorkbench` 过薄

- 无轮询：上传后 status 停在 processing 需手动刷新
- 复核表单未提交付款/收款账号（后端 schema 支持，UI 未暴露）
- 错误处理依赖全局 request 拦截，本地 catch 较少
- `direction==='unknown'` 时仍可点分摊（后端 schema 会拒）

---

#### M8. 迁移兼容分支“表已存在则整段 return”

`20260721_add_bank_receipts`：若 `bank_receipt_batches` 已在（empty-baseline），**直接 return**，后续对 formal 表的 `posting_status` 等列也可能被跳过。
依赖 “baseline 已带全量 metadata” 的隐含约定；若 baseline 与 model 漂移，生产库会缺列。

`20260722` 只补 ignore 字段，说明作者已意识到拆分问题——但主迁移仍偏脆。

1. **分摊目标互斥校验**（schema `model_validator` + posting `_validate_allocation`）
2. **发票分摊合计改为必须精确等于价税合计**（修复了“≤”宽松问题）

6. **ILIKE 转义**、合同搜索防通配符注入
7. **public config 收敛**，admin 配置与密钥脱敏
8. **回单文件独立下载接口** + `VIEW_PAYMENTS`（不走裸对象键）
9. **形式记录 `source_*_allocation_id` unique**，防重复入账同一分摊
